# 관리자 진입과 403 반복 차단

403은 서버가 접근을 거절한 결과다. 자동으로 계속 호출하면 안 된다. 수정 전 로컬 재현에서 권한 거절·캐시 제거·활성 조회 재생성이 반복되어 약 1.2초 관찰 중 `/api/admin/me`가 678회 호출되었다. 이는 고정 간격 polling 설정이 아니라 거절 후 캐시 제거로 생긴 재조회 루프였다.

AdminShell은 같은 세션에서 관리자 API의 401/403을 받으면 승인 데이터 제거와 함께 권한 조회를 비활성화한다. 경로 변경과 포커스 복귀도 거절 상태에서는 재요청하지 않는다. 설정의 관리자 링크에도 같은 중단 처리를 적용했다. 새로운 로그인/세션에서는 다시 확인하며, 관리자 화면의 명시적인 ‘권한 다시 확인’은 수동으로 한 번 요청할 수 있다. 일반 오류와 달리 401/403 거절을 자동 복구하지 않는다.

거절 사실은 QueryClient 승인/데이터 캐시와 별도로 현재 로그인 세션에만 보관한다. 쿼리 캐시 제거·관찰자 재생성이 일어나도 추가 HTTP 권한 요청을 보내지 않는다. 이전에 시작한 200 응답이 늦게 도착하더라도 다른 관리자 요청에서 이미 거절되었다면 승인으로 되돌리지 않는다. 수동 재확인은 이 거절 기록을 명시적으로 해제하며, 확인 중 버튼은 중복 제출을 막는다. 이 기록은 브라우저 저장소에 영속 저장하지 않는다.

명시적인 USER access claim은 프론트가 관리자 진입을 일찍 거절하는 데만 사용한다. ADMIN claim을 읽었다고 승인하지 않으며 반드시 `/api/admin/me`의 서버 승인과 ADMIN 응답이 필요하다. 잘못된 형식/변조된 토큰도 서버의 서명 검증을 우회하지 못한다. 설정 링크나 URL 숨김은 보안 경계가 아니다.

토큰 갱신과 응답 헤더 회전에서는 issuer/sub/sid/role이 모두 같은 경우에만 같은 UI 세션을 유지한다. 역할·계정·로그인 세션이 바뀌면 UI 세션 번호를 올려 기존 관리자 승인·회원 조회 캐시를 폐기한다. JWT payload의 이 비교는 UI 캐시 분리 용도이며 인증 승인을 대신하지 않는다. 일반적인 같은 계정/권한의 토큰 갱신에서는 연습 상태를 유지한다.

로컬 브라우저 검증은 거절 후 `/admin/me` 1회, 포커스 복귀 시 추가 0회, 위조 ADMIN 승인 거절, USER 사전 거절(관리자 요청 0회), 계정 전환 시 이전 회원 데이터 제거 및 설정 링크 거절 후 중단을 확인한다. 테스트는 API 대역이며 운영 회원 계정의 역할·실제 데이터 열람 원인은 별도 `/api/admin/me`, `/api/users/me`의 id/role/상태로 확인해야 한다. 토큰 원문은 수집하지 않는다.

검증 결과: 접근 차단 브라우저 시나리오 5개와 기존 관리자 브라우저 시나리오 32개, 인증·세션·접근 관련 자동 테스트 39개를 통과했다. 최초 SSR와 브라우저 hydration이 같은 화면에서 시작하도록 브라우저 자격 확인 전에는 권한 쿼리를 실행하지 않는다. 프로덕션 빌드와 변경 코드 ESLint도 통과했다.
