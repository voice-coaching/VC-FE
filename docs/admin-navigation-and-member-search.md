# 관리자 화면 전환 및 이름 검색 개선 (#102)

## 사용자 동작

- 관리자 첫 진입 시에는 서버 승인을 기다린다.
- 같은 로그인 세션에서 메뉴를 이동할 때는 이미 승인된 관리자 화면을 유지하면서 권한을 백그라운드에서 재확인한다. 권한 확인 중이라는 전체 화면을 반복 표시하지 않는다.
- 재확인 중 입력한 내용도 승인 응답 때문에 사라지지 않는다.
- 권한 없음(401/403), 세션·계정 변경은 기존처럼 즉시 관리자 화면을 차단하고 이전 계정의 조회 캐시를 지운다. 확인 실패를 새로운 승인으로 판단하지 않는다.
- 회원 관리의 평가번호·UUID 조회 영역은 제거한다. 상단 이름 검색에 회원의 이름(닉네임)을 넣고 조회한다. 비워서 조회하면 전체 목록으로 돌아간다. 상태·권한 필터와 페이지 조회는 유지한다.

## 구현 경계

AdminShell의 세션별 경계를 유지하고 React Query의 keepPreviousData를 권한 조회에 적용했다. 경로별 쿼리와 매번 수행하는 서버 요청, staleTime=0·gcTime=0·HTTP no-store는 유지한다. 같은 쿼리 관찰자의 이전 승인 값을 다음 조회가 대기하는 동안 UI에만 사용한다. 권한 응답을 장시간 보관하거나 재검사를 생략하는 변경이 아니다. 다른 계정은 별도 컴포넌트로 재생성하므로 이전 승인 값을 사용할 수 없다.

회원 검색은 기존 GET /api/admin/users?keyword=...&page=0&size=20을 사용하고 앞뒤 공백을 제거한다. 이름은 현재 회원 모델의 nickname이다. 별도의 실명 컬럼이나 전용 이름 검색 API를 새로 만들지 않았다. 기존 백엔드 keyword는 다른 회원 식별 필드도 검색할 수 있지만 이 UI는 이름 검색으로 안내한다. 프론트의 /users/resolve 호출·전용 타입·입력 검증 함수는 제거했고 백엔드 API 자체는 변경하지 않았다.

관리자 일반 조회·삭제·편집·발송 API는 계속 서버에서 현재 권한을 검증한다. 일반 사용자 화면과 관리자 입장 링크의 권한 정책은 변경하지 않는다.

## 검증 항목

1. 권한 응답을 의도적으로 지연한 상태에서 메뉴·회원 검색 입력이 유지되고 전체 확인 화면이 표시되지 않는지 확인.
2. 메뉴 이동마다 /admin/me 재확인이 실제로 발생하는지 확인.
3. 이전 승인 후 다음 응답이403이면 관리자 메뉴와 기존 회원 데이터가 즉시 사라지는지 확인.
4. 다른 계정으로 전환하거나 익명 상태로 진입하면 이전 승인 정보를 사용하지 않는지 확인.
5. 한글 이름·앞뒤 공백·없는 이름·빈 검색·목록 복귀를 확인. /users/resolve 호출이 없어야 함.
6. 기존 관리자 삭제·음성·초안 편집·모바일·권한 테스트를 함께 확인.

브라우저 검증은 localhost와 모의 API만 사용하며 운영 회원을 조회·수정하거나 실제 알림을 발송하지 않는다.

## 실행 결과 (2026-11-03)

서비스·캐시 테스트25개, 관리자 Chrome 브라우저31개, 기존 API 계약90개와 토큰 갱신 검증이 통과했다. 변경 파일 ESLint·TypeScript 검사·프로덕션 빌드도 통과했다. 지연된 재확인 중 화면과 입력 유지, 경로 이동별 권한 재검사, 승인 후403 차단, 계정 변경 차단, 이름 검색·빈 결과·전체 복귀를 검증했다. 운영 API에는 실제 변경 요청을 보내지 않았다.
